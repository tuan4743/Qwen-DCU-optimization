# 02 · 关于"最有价值的是算子融合"的说明

> 一句话:这份仓库里的最终成果按终稿说明文档为准——**五轮优化全部落地,其中第四、五章的算子融合是单轮收益最大、最后把成绩推到顶的部分**。早期记录(截至 07-13)曾说"算子方向是死路",那是**过时结论**,特此说明原因。

## 为什么早期记录与最终结论不同

**时间差**:早期任务文档(01-19)记录到 2026-07-13 为止。那时能看到的一个"点亮瘦 GEMM 链"的改动(C1)和一条**手写算子集成失败的路线**。而五轮优化的其余部分(尤其算子融合)是在 07-14/15 的评测窗口完成并验证的,不在早期文档的记忆里——形成了"记录说死路、实际已做出"的断层。

**两个"融合"不是一回事**(关键区分):
- 早期 B10 判死的是:**把"投影 GEMM + 递归核"揉进一个 kernel** 的跨算子融合——它收益上限只有约 5%,确实不值得,这个判断本身没错。
- 最终落地的是:**权重拼接(跨阶段 in_proj 融合)、瓦片与调度层面的调优、融合 Chunk 预处理**——对象完全不同,收益大得多,而且全部是 Python 模型层 + 自带 Triton/FLA 改动,**不需要重编译 C++ 算子**。四、五章就是这个。19 号文档的"融合死路"结论应视为只对前者成立。

## 怎么确认最终结论可信

- 逐轮成绩单调上升(12.20 → 16.20 → 17.25 → 19.12 → 19.56),非单点波动;
- 每个改动有截图佐证(仓库 `optimization_records/attachments/`,40 张,含改动前后代码与指标对比);
- 15 处改动在 `01_final_changes_spec.md` 中有完整对照,可与 `vllm_final/`(最终代码)逐条核对;
- 最终成绩(19.56/14.92/12.22、TTFT 1964ms、TPOT 45.14ms)以说明文档汇总表为准。

## 如果你想继续在这条路上走

1. 先看 `01_final_changes_spec.md`:15 处改动的"改前/改后"对照,照抄即可;
2. 新卡上线的顺序建议:先做 1.1(点亮算子链,收益最大、风险最低),再按轮次推进,每轮之后复测指标;
3. 特别注意:瘦 GEMM 路由的 k>8192 硬封顶与 `TORCH_BLAS_PREFER_HIPBLASLT=0` 是数值与性能双保险,不要去掉。
